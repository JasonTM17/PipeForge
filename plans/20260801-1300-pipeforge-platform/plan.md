# PipeForge production-oriented distributed data platform

## Overview

PipeForge is a from-scratch monorepo for distributed dataset processing. The Go control plane owns identity, metadata, job lifecycle, scheduling, leases, outbox/inbox processing, and public APIs. The Python data plane consumes versioned commands, processes CSV/JSONL/Parquet data in bounded chunks, writes artifacts to MinIO, and publishes result events. This workspace has no existing application code or README, so the attached PipeForge specification is the requirements baseline and Phase 1 creates the missing project context.

## Architecture Decisions

1. Go `chi` + `pgx` + explicit SQL: lightweight HTTP routing and clear transaction boundaries; avoid ORM behavior hiding state transitions.
2. PostgreSQL is the control-plane source of truth. SQL migrations are versioned and all lifecycle transitions are explicit commands with history rows.
3. RabbitMQ uses durable exchanges/queues, publisher confirms, manual acknowledgements, bounded retries, and DLQs. Message envelopes and payloads are JSON Schema versioned.
4. MinIO stores immutable raw dataset versions and attempt-scoped artifacts. Object keys are generated by the server, never accepted as authoritative input.
5. Python uses Polars for bounded, memory-conscious CSV/JSONL/Parquet processing, with adapters isolated behind reader and processor protocols.
6. At-least-once delivery is assumed. Go result consumers use inbox deduplication plus lease/attempt validation; Python workers make artifact publication attempt-scoped and idempotent.
7. Local Docker Compose is the reference environment. Kubernetes, cloud deployment, and external credentials remain out of scope.

## Acceptance Criteria

- A new checkout can bootstrap and start PostgreSQL, RabbitMQ, MinIO, Prometheus/Grafana, Go services, and a Python worker from documented commands.
- Users can register/login/refresh/logout, create scoped API keys, and access only owned/authorized resources.
- Small uploads stream through Go without buffering the full file; multipart uploads support initiation, parts, completion, abort, expiry cleanup, checksum, and immutable versions.
- Jobs are created idempotently, create an outbox row in the same database transaction, publish through RabbitMQ, and expose controlled lifecycle endpoints only.
- Python processes CSV, JSONL, and Parquet in chunks; profiling, quality rules, IQR/Z-score anomaly detection, bounded progress, cancellation, and attempt-scoped artifacts work.
- Go remains authoritative for result acceptance, artifacts, state history, leases, retries, dead letters, and duplicate/stale message handling.
- Unit, integration, contract, end-to-end, security, and race/build checks cover happy paths and failure paths without committed secrets.
- Architecture, ADRs, API/messaging contracts, threat model, testing strategy, operational runbooks, and CI workflows match the implemented behavior.

## Verification and Commit Policy

- Each phase starts with a narrow test/design check and ends with the relevant Go/Python/contract/integration checks.
- Stage explicit file lists; never use blind `git add .`. Run secret scanning before every commit.
- Use small Conventional Commits grouped by one coherent behavior. Do not create empty commits merely to mirror the specification's baseline list.
- After each commit report hash, message, changed components, commands, test result, and next commit. A commit is allowed only when the repository remains buildable or the commit is a documented foundation step that establishes the next runnable slice.
- Final gates: fresh validation evidence, adversarial review, docs sync, clean secret scan, CI-equivalent checks, and a release-ready status.
